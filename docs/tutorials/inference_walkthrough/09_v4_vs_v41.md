# 09 V4 与 V4.1：复用发生在哪个层级

## 1. 比较边界

本章比较当前 fork 的独立代码；不根据 V4.1 名字推测官方架构规格。[官方] 已核实的 DeepGEMM 固定版支持 GEMM、indexer 和 MegaMoE 机制，不能据此证明 V4.1 checkpoint 的层数、source IDs 或性能。V4/V4.1 模型卡与论文版本本次未获取，官方设计与本地实现的等价性列为未验证。

最核心的问题是：复用的是临时 buffer、planner、top-k **结果**，还是持久 KV **内容**？V4 的同层类型 planner 和通用 top-k 工作 buffer 复用，不等于 V4.1 的 source/consumer 架构。

## 2. 从三层教学拓扑建立直觉

[教学] layer0 是 KV/index source，layer1 是 consumer，layer2 是新的 index source；三层都保持自己的 SWA。layer1 用 layer0 的长程压缩 KV 与最新 top-k 结果；layer2 可针对自己的 Q 再打分，而 key cache 仍来自最近 KV source。这组 IDs 是解释用，不是实际模型卡字段值。

~~~mermaid
flowchart TD
  L0["layer0: KV source + index source"] --> C["压缩 Attention KV / index K cache"]
  L0 --> T0["发布 top-k"]
  C --> L1["layer1: consumer，自己的 Q/SWA"]
  T0 --> L1
  C --> L2["layer2: index source，复用 index K"]
  L2 --> T2["刷新 top-k / 可选候选 block"]
  T2 --> N["后续 consumers"]
~~~

[vllm/models/deepseek_v41/attention.py · DeepseekV4Attention.__init__ · L274–L657](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/attention.py#L274-L657) 用 max(source <= layer_id) 定位最近 source；kv_source_layer_ids 与 index_source_layer_ids 必须由 config 提供。consumer 如果在本 PP rank 找不到 source，会抛 NotImplementedError，不能把共享 group 从中间任意切开。

## 3. 逐项差异：设计、代码、shape、工作量、指标

| 机制 | V4 [代码] | V4.1 [代码] | shape / 工作量与可能影响 |
| --- | --- | --- | --- |
| compress_ratios | max(1,c)，主要分支 1/4/128；1 为 SWA-only | 0/1/2，0 为 SWA-only，1 仍有长程 cache | 不能用同一 c<=1 条件；c 更小增加记录数，但 source 共享减少独立 cache 数 |
| 主 compressor | 每个 c>1 层自有 | 只在 is_kv_source 层构建 | consumer 少主压缩投影、state save、cache insert；不是删除 Q/SWA |
| 压缩 KV ownership | 每 c>1 层 spec | 非 source 返回 None，读 source.kv_cache | 长程容量按 source 层数求和；consumer Attention 历史读取仍存在 |
| indexer | c=4 层自己的 indexer 和 compressor | 只在 index source 存在，非 KV-source indexer 复用 index K | 减少 indexer 执行层数、key cache 数；Q 与 score 更新频率变低 |
| 主/索引压缩生产 | 两条独立 compressor 分支 | main latent 供主 KV insertion 和 index K projection/store | 减少重复压缩；key 生成依赖 latent，不能提早读 |

| Q quant sharing | shared RMSNorm 后分别投影/量化 | 满足量化方法兼容和 r_q%32=0 可共享量化 Q 与 scales | 少重复 quant/读写，见 _split_qkv_and_norm |
| O / mHC / Mega attention | FP8 grouped O 与 mHC kernels | 有 GEMM-RS、all_reduce_mhc、mega_mhc / mega_attn 条件路径 | collective 可能进入 fused op，不应凭 trace 少了 NCCL 就说无通信 |
| MoE | 前num_hash_layers可查token->expert表；其他层learned sqrtsoftplus / correction bias | V4.1 NVIDIA MoE继承V4 base，但显式传num_hash_layers=0；并扩展deferred finalize | 本路径取消hash expert选择，改变查表/负载分布；不能据此断言增加一整次gate GEMM，V4 hash路径也可计算gate scores |
| 额外状态 | 本教程文本主线 | Engram、replay 与视觉相关路径存在 | 增加 lookup/表/控制与可能通信，不能只比较 Attention FLOPs |

## 4. cache 容量要算 source 数与记录数

两版MoE的继承关系不能掩盖参数差异：V4.1构造函数明确把num_hash_layers固定为0，所以不能把V4的token->expert查表路径当作V4.1行为。V4.1还可对DSpark/MTP位置使用单独的expert数和TopK配置；[vllm/models/deepseek_v41/nvidia/model.py · DeepseekV4MoE.defer_finalize · L154–L174](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/nvidia/model.py#L154-L174) 仅在兼容的modular TRTLLM MXFP4 experts等条件下把top-k归并交给后续all-reduce+mHC，不代表普通AG/RS路径也自动使用同一融合。

V4.1拥有index K的source会把主compressor的pre-RoPE latent通过复制权重wk=[d_idx,d]映射成key；逻辑输入[T,d]、输出[T,d_idx]，但只有压缩组边界对应的行能写cache。随后Norm/RoPE/量化store。非owner index source不重复产生key，而对自己的Q重新打分。相较V4的独立hidden-state index compressor，减少的是那条hidden->index压缩生产链，新增/保留的是latent->key投影；稀疏Attention消费者仍读取历史key/主KV。

长程 cache 的内容容量近似（先忽略 block/page 对齐）：

~~~text
V4:   sum_over_compressed_layers floor(L/c_layer) * b_layer
V4.1: sum_over_KV_sources        floor(L/c_source) * b_source
~~~

再加每层 SWA、index K、compressor state、workspace、各 group padding。不能仅比较“4 倍压缩”与“2 倍压缩”就断言 V4.1 显存更大或更小。

[教学] L=1024，四个 V4 c=4 层使用584 B记录：4*256*584=598,016 B。若 V4.1 两个 c=2 source 使用528 B：2*512*528=540,672 B。若只保留一个 source 又不同。这个数字不是实际模型的层拓扑，也未计 SWA/indexer，不能变成模型显存结论。

[vllm/models/deepseek_v41/attention.py · DeepseekV4Attention._compressed_kv_cache · L1165–L1172](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/attention.py#L1165-L1172) 从 static_forward_context 返回 source cache。复用不需要跨 rank collective，因为本 TP rank 已有对应 source 的 cache；普通 TP 各卡仍复制它。跨 source 更换、候选刷新、indexer 执行对齐属于模型层内依赖，不能把不同请求的 top-k buffer 串用。

## 5. prefill/decode、SM90/SM100 与 replay 条件

两版选择器分别为 [vllm/models/deepseek_v4/nvidia/model.py · _select_dsv4_attn_cls · L1011–L1042](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v4/nvidia/model.py#L1011-L1042) 与 [vllm/models/deepseek_v41/nvidia/model.py · _select_dsv4_attn_cls · L197–L243](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/nvidia/model.py#L197-L243)。V4显式FlashMLA DSV4分支返回普通sparse类；V4.1支持自己的FLASHMLA_SPARSE_DSV41以及FLASHMLA_MEGA_ATTN_DSV41，默认SM100还会先检查Mega attention是否可用。为了复现普通sparse讲解，应记录显式backend与实际类；不能仅看到“SM100+FlashMLA”就假定普通路径。

[vllm/models/deepseek_v41/nvidia/flashmla.py · DeepseekV4FlashMLAAttention.forward_mqa · L76–L165](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/nvidia/flashmla.py#L76-L165) 用 compress_ratio==0 判断 SWA-only，c=1 的 prefill 确实 gather 长程 cache。V4 的 c<=1 路径移植过来会漏读。V4.1 decoder 同时引入条件优化，追踪时应记录实际类、量化格式与 current_platform capability，而不只记录 backend 名。

SWA bounded replay 用已缓存长程状态与窗口重放恢复局部状态；它不是简单“跳过所有命中 token 的全部层”。[vllm/models/deepseek_v41/attention.py · DeepseekV4Attention.__init__ · L274–L657](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/attention.py#L274-L657) 明确：V1 runner 不支持所需 replay 写入跳过，因此关闭；PCP>1 和 ROCm 也有关闭分支。[vllm/models/deepseek_v41/nvidia/model.py · DeepseekV4Model._decoder_replay_supported · L1202–L1239](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/nvidia/model.py#L1202-L1239) 对 decoder replay 还排除 SP、microbatch、不合适的 PP 切分、晚期 Engram、某些 draft 窗口。

因此第7章 TP2/DP4 的 SP 主线不能同时被宣传成 decoder bounded replay 已生效。引入 V2 要另读 [vllm/v1/worker/gpu/model_runner.py · GPUModelRunner · L191–L2390](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/v1/worker/gpu/model_runner.py#L191-L2390)、V4.1 model_state 与 replay batch 的 metadata；主线的 V1 调用路径不自动迁移为 V2 路径。

Engram 是当前 V4.1 另一个持久 lookup/table 机制，[vllm/models/deepseek_v41/common/engram.py · EngramLayout.from_config · L246–L249](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/common/engram.py#L246-L249) 与 [vllm/models/deepseek_v41/nvidia/model.py · DeepseekV4Model.forward · L912–L1077](https://github.com/jia0713/vllm/blob/10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf/vllm/models/deepseek_v41/nvidia/model.py#L912-L1077) 存在可选 DP 分片查表、预取和共享内存分支。本教程只定位它对状态、通信与 trace 分析的影响，不在缺少 checkpoint 下填入 table 规模或把它等同 KV cache。

## 6. 哪些通信变了，哪些没有证据

减少 source/指数打分次数通常减少本地 compute/HBM 工作，不直接消除 TP 的 O projection 归约或 MoE dispatch/combine。GEMM-RS 和 all_reduce_mhc 可以把通信与计算组合进入其他 op，改变 launch 与数据依赖。没有真实 trace，不能断言通信全被隐藏。

MoE base继承关系保留许多learned routing机制，但V4.1本地NVIDIA路径显式关闭hash层；真实checkpoint还可配置不同E/k/I，相关量会改变expert M和路由metadata。我们没有固定模型config，因此对两模型的每层绝对FLOPs、总KV、通信字节及速度均不下结论。
